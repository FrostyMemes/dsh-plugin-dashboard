# Совместимость с DeepSeek Harness Desktop

## Свободная версия runtime (2026-10-19)

По прямому указанию пользователя плагин `0.1.2` принимает любую версию DSH: `engines.dsh` и все peer requirements равны `*`. Установленный официальный `dsh-app-boot` проверяет `engines.dsh` с `semver.satisfies(..., { includePrerelease: true })` и отдаёт ему приоритет, поэтому alpha/rc версии также принимаются. Исключения `allow-version` не добавляются, код Harness не меняется.

Конкретные версии Harness `0.2.1-rc.2` и Cordis `4.0.5` оставлены в devDependencies и lockfile для воспроизводимой разработки. Это снятие ограничения установки, а не подтверждение совместимости с будущими API. При изменении API возможна ошибка активации или работы плагина. Ранее зафиксированные проверки ниже относятся к указанным в них версиям.

## Текущее решение и следующий проверяемый шаг

Исходники плагина реализуют pairing-путь из утверждённого плана: кнопка Bundle запрашивает у Host Remote случайный одноразовый токен с TTL 2 минуты; токен передаётся во fragment URL; API обменивает его на подписанную HttpOnly/SameSite cookie с TTL до 30 дней, привязанную к `127.0.0.1:<port>`. Cookie signing key хранится через DSH Credentials. SPA, snapshot и SSE обслуживаются собственным loopback prefix route. Самостоятельный route проверяет Host, Origin и Fetch Metadata, а защищённые API дополнительно проверяют cookie. Исправленный `cordis.patch.yml` использует подтверждённый `- insert:` формат; Client entry собирается в формат `window.__ModuleLoader__.load(...)`.

Совместимость проверена частично. Первоначальный компонент доходил до `Running`, но pairing завершался обычным `Error`. Затем startup dialog выявил циклическое ожидание `remote.agentControlCenter`; оно устранено в исходнике: namespace монтируется первым, detail action регистрируется в дочернем fiber после его появления. После перезапуска пользователь подтвердил скриншотом успешный pairing: статус `Connected`, snapshot с одним root agent в состоянии `idle`, известные subagents `0`, четыре token counters (input `7 520`, output `196`, cache read/write `0`, всего `7 716`), модель `deepseek-v4.1-flash`, context estimate `7 690 / 1 000 000`; задача корректно отображается как недоступная, snapshot помечен `Partial`. Метка `Connected` устанавливается обработчиками EventSource `onopen`, `heartbeat` и `snapshot`, что подтверждает открытие SSE и получение начального snapshot. Пользователь затем подтвердил, что live-обновление активной сессии появилось на дашборде. Reconnect после потери потока пока не проверен.

## Ограничения этой проверки

- Проверена одна установка `0.2.0-rc.2`; совместимость с другими версиями не заявляется.
- API и большая часть поведения исследованы по точным файлам поставляемого ASAR и source tag; локальный Bundle установлен, включён и показывает активный компонент. Перечень сессий после перезапуска теперь строится через `sessionQuery.listSessions()`, а не только через `agents.list()`; это реализовано, но восстановление всех видимых сессий после реального перезапуска Desktop ещё не подтверждено.
- Pairing, подписанная cookie, первоначальный snapshot, открытый SSE и live-обновление активной сессии подтверждены скриншотом и сообщением пользователя после исправления circular injection. Источники session title, последнего request-header и archive set подтверждены на установленном ASAR; обновление title, удаление при архивировании, восстановление после reconnect и сортировка требуют тестов плагина и live Desktop. Не проверены остановка/повторная активация Bundle, сценарий с подагентом и полнота token meter. Задача, отсутствующая в источнике, корректно остаётся недоступной; snapshot сообщает `Partial`.
- Декларации типов могут отсутствовать в поставке ASAR; для разработки надо взять совместимые опубликованные типы/пакеты и привязать их к версии `0.2.0-rc.2`, не считать отсутствие `.d.ts` доказательством отсутствия runtime API.
- Установленная версия отличается от текущего upstream `master`; API проверять по установленным файлам и зафиксированному tag.


## Холодное открытие панели после перезапуска (2026-10-18)

Подтверждена ошибка контракта: `readTitleSnapshots(ids)` возвращает `value.title` как `SessionTitleSnapshot`, текст находится в `value.title.title`. Прежний mock со строкой скрывал ошибку; fallback и тестовые ответы исправлены.

В поставляемом `@deepseek-ai/dsh-session-query` `0.2.0-rc.2` подтверждён `observeSession(id)`: read-only observation с `projections.values` и disposer `[Symbol.dispose]`. Для cold session сервис подготавливает неопубликованный Session и восстанавливает проекции, не добавляя live Agent и не возобновляя задачу. Плагин читает только title, tokenUsage, contextPressure, subagentCatalog и собственную проекцию `agentControlCenterLastModel`. Последняя складывает только `request/header.config.model`; исходные промпты, request envelope и `observation.events` панель не читает, не сохраняет и не передаёт. Внутри официального сервиса холодное восстановление может читать лог; это не запуск агента.

Observation освобождается в finally; одновременно читаются до четырёх сессий. Плагин кэширует только выбранные метаданные до загрузки/выгрузки или удаления сессии; ошибки повторяются при следующем обновлении и логируются один раз за непрерывный сбой. Новая live-сессия имеет приоритет над результатом незавершённого cold read. Статус записи без Agent остаётся `unknown`; метрики описывают сохранённую сессию. Проверка restart на Desktop отдельно не выполнена.
