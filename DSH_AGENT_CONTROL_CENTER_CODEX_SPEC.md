## 0. Инструкция Codex: что делать с этим файлом

Реализовать **только MVP**, описанный ниже, в отдельном репозитории/пакете `dsh-agent-control-center`. Начать с проверки API и совместимости **конкретной установленной версии официального DeepSeek Harness Desktop**. Использовать официальные публичные точки расширения и Cordis. **Не модифицировать ядро DeepSeek Harness**, если задача решается через плагин.

Работать по этапам с промежуточными проверками. Для любого метода, имени события, пакета, механизма авторизации, формата Bundle или способа получения текущего порта, не подтверждённого исходниками установленной версии, сначала исследовать API и задокументировать результат. **Первое действие Codex:** зафиксировать в `docs/COMPATIBILITY.md` версию Desktop/runtime и таблицу «возможность → подтверждённый API → путь к исходному файлу/документации → ограничения». Пока эта проверка не завершена, не считать интеграцию готовой.

Для простых, чётко ограниченных исследовательских задач, делегируемых подагентам (например, read-only изучение конкретного API или модуля), использовать модель **GPT Luna 6** (`gpt-6-luna`) с высоким уровнем рассуждения (**High**). Для более сложных задач выбирать модель по их требованиям.

## 1. Задача и сценарий пользователя

Пользователь запускает **официальный DeepSeek Harness Desktop** с одним Host. В нём одновременно существуют корневые агенты и подагенты. Пользователь открывает **обычный браузер** и видит все доступные сейчас состояния системы в **реальном времени**, не переключаясь между сессиями Desktop.

Основные сценарии:

1. Видеть сетку карточек агентов с названиями, состояниями, задачами, моделями и метриками.
2. Видеть количество непосредственных и вложенных подагентов каждого агента.
3. Переключаться между сеткой и иерархическим деревом агент → подагенты.
4. Просматривать контекстное окно и статистику токенов (с честным указанием точности и доступности).
5. Открывать подробную страницу выбранного агента.
6. Видеть изменения **автоматически**, без перезагрузки страницы.
7. Пользоваться интерфейсом на разных мониторах: число колонок выбирается по **доступной ширине окна**, без ограничения тремя.

## 3. Что считается агентом и что показываем

В главном Dashboard:

- **Живые агенты одного Host** из реестра (`ctx.agents.list()` — если доступно в версии пользователя).
- **Известные подагенты**, обнаруженные из каталогов родителей; их сессия может существовать, когда живого Agent-объекта нет. Такие элементы не следует маркировать как `running` без подтверждения.
- Никаких «вообще всех агентов на компьютере», сторонних процессах или аккаунтах; один Host — граница MVP.
- Внешние провайдеры показывать в той мере, в какой Harness раскрывает их каталоги. Если ветка недоступна, обозначить `visibility: partial/unsupported`, а не рисовать нулевое количество потомков как полную истину.
- Исторический глобальный просмотр **всех** сохранённых сессий не обязателен в MVP; сохранённые дочерние элементы допускаются как известные узлы дерева. Не запускать/не возобновлять сессии ради просмотра.

**Три независимых аспекта состояния:**

1. `runtimeStatus`: `running | idle | not_loaded | unknown | disconnected`.
   - `running`, `idle` — подтверждённые состояния живого агента.
   - `not_loaded`, `unknown`, `disconnected` — диагностические состояния мониторинга, а не нативные статусы Harness.
2. `lastOutcome`: `completed | aborted | blocked | error | max-tokens | interrupted | forked | unknown`, только если действительно известен; иначе `unknown`.
3. `dataFreshness`: `live | stale | unavailable` с `observedAt`.

**Запрещено:** считать `idle` успешным завершением задачи, а `disposed` отдельным состоянием живого агента; выдавать отсутствие метрики за ноль; создавать «фазы мышления» или «текущие мысли модели» из догадок.

### 4.4. Главный экран

**Сверху:** название `DSH Agent Control Center`, индикатор `Connected / Reconnecting / Disconnected`, время последнего обновления, кнопка копирования URL (при необходимости).

**Сводные счётчики:** `Live agents`, `Running`, `Idle`, `Known subagents`, `Last errors`, `Tokens (available)`. У каждой цифры ясно обозначить область подсчёта. Не суммировать один и тот же узел дважды.

**Карточка:**

- Имя/label, тип `Root / Subagent / External`, ID (copy), model/provider.
- Живой статус, бейдж последнего результата (если есть), свежесть данных.
- Краткая текущая задача (только если она доступна безопасным способом; иначе `Задача недоступна`).
- Текущая операция (если подтверждена), время выполнения, последняя активность.
- Прямые дети / все доступные потомки / работающие дети.
- Контекст: `X / Y tokens`, процент/бар **только если знаменатель достоверен**; рядом индикатор `estimated` или `provider reported`.
- Input / output / cache tokens — отдельные числовые счётчики. **Не рисовать проценты к произвольным пределам.** Состав токенов можно показывать как относительную долю от общего known-total с явной подписью.
- Действие `Подробнее`.

**Страницы/режимы:**

1. `Dashboard` — сетка карточек.
2. `Agent Tree` — родитель → потомки, статусы, обозначения недоступных ветвей.
3. `Agent Details` — Overview, Subagents, Context & Tokens, Execution, Technical.

**Не делать:** полноценный Timeline, графики истории, отправку команд агентам.

## 5. Real-time: обязательная семантика

Событийное обновление — **не polling каждые N секунд**.

1. В Host плагин подписывается на события создания, изменения статуса, удаления и доступные события сессий/каталогов/токенов.
2. Строит версионированную in-memory проекцию общего состояния.
3. Новый браузер получает **снимок** (`snapshot`) и начинает получать **дельты** (`upsert`, `remove`, `connection`, `resync_required`) по выбранному транспорта.
4. Для MVP предпочитается **SSE (Server-Sent Events)** на same-origin HTTP-маршруте плагина при условии поддерживаемого API и безопасной авторизации. Если фактическая версия Harness делает интеграцию через свой WebSocket/Connection более корректной — Codex обязан обосновать и документировать выбор.
5. События несут `revision` (монотонный номер в рамках boot/epoch), `serverTime`, `entityId`, `payload`.
6. На переподключении/смене boot epoch клиент выполняет **полный snapshot**. Не полагаться на отсутствие пропущенных событий.
7. Сервер посылает heartbeat для обнаружения пропавшего соединения. Браузер отмечает stale после заданного таймаута, отображает `Reconnecting` и использует ограниченный exponential backoff с jitter.
8. Не пересчитывать `ctx.tokenMeter.measure()` при каждом рендере/heartbeat: измерения выполнять при релевантных изменениях и с debounce; избегать `O(surface)` перегрузки.
9. Вкладки браузера не должны создавать новых Agent/Session; подписки на Host общие, а на вкладку расходуются только транспортные ресурсы.

**SLO MVP:** при нормальной локальной работе изменение должно отражаться в браузере в пределах **2 секунд после того, как событие стало доступно Collector**. Это целевое требование, не гарантия реакции на внутренние изменения провайдера, о которых Harness не сообщает.

План восстановления: отвал SSE → UI `stale/disconnected` → reconnect → новый snapshot → продолжение дельт. После горячей перезагрузки плагина обязательно освобождать все подписки и закрывать старые соединения.

## 6. Точки данных из официального Harness

**Верифицированные в документации upstream как кандидаты для привязки** (сигнатуры проверить в установленной версии):

- `ctx.agents.list()` — живые агенты.
- `agent/created`, `agent/status`, `agent/disposed`, `agent/error` — жизненный цикл.
- `ctx.subagents.listChildren(parentSessionId)` — непосредственные каталожные дети.
- `ctx.subagents.listDescendants(rootSessionId)` — доступные каталожные потомки, depth, parent, диагностика ветвей.
- `ctx.tokenMeter.measure(session)` — оценка давления и surface через session log; без запроса к модели.
- Session projections `tokenUsage`, `contextPressure`, `contextBreakdown` — использовать, если доступны.
- Вместимость контекстного окна — из metadata точного маршрута provider/model (официальная документация токенметра указывает `ctx.llm.resolveModelInfo().context`); проверять пустые и меняющиеся значения.

**Источники:**

- https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/core.md
- https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/subagent.md
- https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/token-meter.md
- https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/framework/events.md

**Тонкости:**

- `listDescendants` не обязан обнаруживать все Session forks, внешние ветви или недоступные каталоги. Возвращать диагностику полноты.
- У `Agent.id` может быть идентичность сессии; отдельно вести идентичность runtime-instance/boot, чтобы корректно обрабатывать dispose и resume.
- Не путать runtime-owner/родительскую связь с долгоживущим каталожным отношением.
- `running`/`idle` не подтверждает успешность предыдущего turn.
- `ctx.tokenMeter.measure()` может возвращать **оценочные** значения, а не платёжно точные токены.
- Не показывать «внутренние рассуждения» модели как доступную метрику.

## 7. Нормализованная модель данных

Создать shared TypeScript-типы с nullable/optional полями там, где источник не гарантирован. Рекомендуемая контрактная форма:

```ts
type RuntimeStatus = 'running' | 'idle' | 'not_loaded' | 'unknown' | 'disconnected';
type Freshness = 'live' | 'stale' | 'unavailable';
type AgentKind = 'root' | 'subagent' | 'external' | 'unknown';
type Visibility = 'complete' | 'partial' | 'unsupported' | 'unknown';

type MeasuredNumber = {
  value: number | null;
  source: 'provider' | 'token-meter' | 'projection' | 'derived' | 'unavailable';
  estimated: boolean;
  observedAt: string | null;
};

type AgentView = {
  id: string;                    // локальный уникальный ключ записи в рамках boot
  sessionId: string;
  bootId: string;
  parentSessionId: string | null;
  kind: AgentKind;
  name: string;
  model: string | null;
  provider: string | null;
  runtimeStatus: RuntimeStatus;
  lastOutcome: string | null;
  freshness: Freshness;
  observedAt: string;
  createdAt: string | null;
  lastActivityAt: string | null;
  activeSince: string | null;
  taskTitle: string | null;
  currentOperation: string | null;
  directChildren: number | null;
  knownDescendants: number | null;
  activeDescendants: number | null;
  descendantVisibility: Visibility;
  contextUsed: MeasuredNumber;
  contextWindow: MeasuredNumber;
  contextPercent: MeasuredNumber;
  inputTokens: MeasuredNumber;
  outputTokens: MeasuredNumber;
  cacheReadTokens: MeasuredNumber;
  cacheWriteTokens: MeasuredNumber;
  lastErrorSummary: string | null;  // безопасная краткая формулировка, без секретов
};
```

Это **пример контракта**, допустимо развить типы по итогам исследования. Приоритет — точность смысловых различий.

**Контекст:** `contextPercent = contextUsed / contextWindow * 100` только при совместимых срезах/единицах и валидном `contextWindow > 0`; иначе `null`. Суммарные токены за сессию **не делить** на контекстное окно. Для значения `>100%` не прятать проблему в данных: отображать бар максимум 100%, а фактическое число/диагностику отдельно.

## 8. Backend и браузерный API

### 8.1. Топология

- **Один** официальный Desktop Host — источник данных.
- Host Plugin (Cordis) работает в его процессе; не стартует второй Harness.
- Плагин использует совместимый WebServer/Host API для HTML, API и событий.
- Browser UI загружается отдельной обычной страницей; нельзя полагаться на Electron preload, `dsh-app://` или специфическую Desktop-авторизацию.
- **Важно:** актуальный официальный Desktop по README слушает **системно назначенный порт (OS-assigned)** и `127.0.0.1` по умолчанию. **Не фиксировать порт 19387 или 3080.** Выбрать способ определения текущего URL через поддерживаемый Host runtime API/Plugin Manager и предоставить пользователю copy/open link. Если автоматическое определение не поддержано — задокументировать и предложить корректную процедуру, не гадать порт.

Источник: https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/desktop/README.md

### 8.2. Маршруты — проектный контракт

Префикс (пример, адаптировать к Host): `/agent-control/`.

- `GET /agent-control/` — SPA shell.
- `GET /agent-control/api/v1/overview` — счётчики, статусы, boot/version.
- `GET /agent-control/api/v1/agents` — нормализованный список, фильтры.
- `GET /agent-control/api/v1/agents/:id` — подробная информация.
- `GET /agent-control/api/v1/tree?root=...` — дерево или лес.
- `GET /agent-control/api/v1/stream` — SSE (или эквивалент интегрированного транспорта).
- `GET /agent-control/api/v1/health` — безопасный результат здоровья с минимальными данными.

API **read-only**, JSON с явной версией схемы. Пагинация/ограничение размеров там, где возможны длинные списки. Не раскрывать полные логи, токены авторизации, prompt/tool arguments, секреты в ответах.

### 8.3. Авторизация — обязательный блокирующий критерий

Пользователь открывает самостоятельный Dashboard в обычном браузере. Такая вкладка **не обязана наследовать доверенную сессию Electron**. `localhost` сам по себе **не равен аутентификации**.

Внешние маршруты `webServer.register()` **не считать автоматически защищёнными** проверками браузерной сессии Harness. Сперва исследовать фактическую версию. Известное обсуждение upstream:
https://github.com/deepseek-ai/deepseek-harness/discussions/5770

Два допустимых способа:

1. **Предпочтительно:** штатный документированный браузерный auth/context текущего Host, **если** он действительно распространяется на зарегистрированные плагином API/SSE-маршруты и тестируется без Electron.
2. **Если нет:** собственная минимальная защищённая loopback-аутентификация плагина (одноразовая процедура сопряжения браузера с Host; cookie с `HttpOnly`, `SameSite=Strict`, `Secure` при HTTPS; ротация/отзыв; защита от CSRF и cross-origin злоупотреблений). Не передавать долгоживущий секрет в localStorage/URL/log; не раскрывать секрет в API; не оставлять доступ по факту localhost.

В обоих вариантах:

- Только `127.0.0.1` по умолчанию; не биндим `0.0.0.0`.
- Проверять авторизацию **на API и SSE отдельно**, а не только при открытии HTML.
- Проверять Origin/Fetch metadata, безопасные заголовки и CSP, не включать произвольный CORS.
- Не передавать аккаунтные токены/секреты DeepSeek в страницу.
- Продумать HTTPS/security для нестандартных сценариев; сетевой доступ из LAN **не входит** в MVP.
- Без разрешённой безопасной схемы авторизации **не запускать функциональный API** и не заявлять MVP готовым.

## 9. Архитектура компонентов

```text
Official DeepSeek Harness Desktop (ONE Host)
  ├─ AgentRegistry / Events / Sessions / Subagent Catalog / TokenMeter
  └─ DSH Agent Control Center (Cordis Host plugin)
      ├─ AgentCollector           lifecycle/status/current runtime state
      ├─ SubagentResolver         parent/child relationships + diagnostics
      ├─ TokenMetrics            token context (debounced, typed sources)
      ├─ AgentStateStore         versioned in-memory normalized projection
      ├─ ApiController           read-only endpoints & permissions
      ├─ RealTimePublisher       event stream, heartbeat, resync
      └─ WebAssets              serves browser UI
            |
            +---- same-origin authenticated HTTP + SSE ---->
                       Browser (React UI)
                         ├─ Dashboard
                         ├─ Agent Tree
                         └─ Agent Details
```

Для подписок использовать Cordis effects/`ctx.on`, корректно освобождать при unload/hot reload. Не держать тяжелые подписки/перечитывание логов на каждую открытую вкладку.

**Memory state:** in-memory only. Полные сессионные логи не копировать и в отдельную БД не класть. Перезапуск Host допустимо сбрасывает временные метрики и выполняет новый snapshot.

## 11. План работ и контрольные точки

### Этап 0 — Compatibility Spike (обязателен)

1. Определить версию официального Desktop и связанного DSH runtime.
2. Прочитать `AGENTS.md`, `docs/architecture.md`, `apps/desktop/README.md`, руководство по плагинам, Cordis и API.
3. Проверить присутствие `ctx.agents`, `ctx.subagents`, `ctx.tokenMeter`, событий и доступного WebServer.
4. Установить **точную** процедуру доставки Host-плагина в профиль `desktop` (через встроенный Plugin Manager / поддерживаемую установку bundles). Документация Desktop допускает альтернативный путь `dsh plugin --profile desktop ...` **после полного выхода** из Desktop, но не подразумевать, что это единственный путь.
5. Найти поддерживаемую реализацию самостоятельной обычной браузерной страницы, безопасной авторизации и определения её актуального адреса при динамическом порте.
6. Создать `docs/COMPATIBILITY.md` с подтверждёнными/недоступными возможностями.

**Gate:** если нет безопасного браузерного доступа из Host, остановиться и подготовить короткий отчёт с альтернативой. Не делать публичный незащищённый HTTP endpoint ради демонстрации.

### Этап 1 — Базовый сборщик

- Подписаться на `agent/created`, `agent/status`, `agent/disposed` и необходимые события.
- Создать начальный snapshot из реестра живых агентов.
- Реализовать нормализованный in-memory state, безопасное извлечение задачи/метаданных, revision/bootId.
- Юнит-тесты: создание, работа, простой, удаление, повторное создание ID, пропущенные значения.

### Этап 2 — Подагенты и токены

- Получить `listChildren` / `listDescendants`, хранить диагностические статусы недоступных ветвей.
- Не делать full-tree traversal на каждый status event; кешировать и обновлять при релевантных изменениях.
- Получить token-meter и model-context данные с явным source/estimated.
- Тесты: вложенность, циклы/повторы, неизвестный провайдер, нулевая вместимость, неполный контекст.

### Этап 3 — Защищённый API + события

- Проложить браузерный маршрут и выбранный механизм auth.
- Реализовать snapshot + SSE, heartbeat, revision/bootId и reconnect/resync.
- Тесты: неавторизованный GET/stream отвергается, Origin/CORS безопасен, подписчики не мешают друг другу, обрыв и восстановление не оставляют «вечный running».

### Этап 4 — Визуальный Dashboard

- React приложение, Classic Console Neue (после проверки лицензии), тёмная палитра из §4.
- CSS Grid auto-fit с фактически адаптивным числом колонок.
- Метрики, разноцветные бары, поиск/фильтры, состояние связи.
- Сделать пустые/ошибочные/частичные состояния и responsive скриншоты.

### Этап 5 — Дерево и карточка подробностей

- Переход из карточки → Agent Details.
- Дерево и навигация по root/descendants.
- Чёткое разделение runtime status, last outcome, metadata, token-estimates.
- Тесты корректности дерева и переходов.

### Этап 6 — Интеграция, упаковка, проверка

- Собрать пакет, пригодный для поддерживаемой установки в **официальный Desktop**.
- Проверить hot unload/reload и отсутствие утечек подписок.
- Провести E2E на живом Host с как минимум двумя агентами и одним подагентом (если есть доступ к тестовой среде); без API-ключа использовать тестовые мок-события для unit/UI, **не** выдавать mock за живое подключение.
- Документировать установку, подключение браузера, сопряжение, обновление и удаление.
- Представить отчёт: что работает на фактической версии, где есть ограничения upstream.

## 12. Тест-план и критерии приёмки

### Функциональные

- [ ] При работающем официальном Desktop в обычном браузере открывается Dashboard.
- [ ] Страница соединяется с **тем же** единственным Host, не создавая другой процесс Harness.
- [ ] При запуске двух агентов автоматически появляются две карточки с достоверными ID.
- [ ] `running → idle` меняется без перезагрузки, с целевой задержкой ≤ 2 с после серверного события.
- [ ] Созданный подагент появляется в карточке и дереве, а его статус меняется независимо от родителя.
- [ ] При неизвестных/недоступных подагентах дерево сообщает об ограничении видимости.
- [ ] Детали агента открываются, не возобновляя сессию и не отправляя команд.
- [ ] Контекст не путается с cumulative token usage; неопределённые величины показаны как `Н/Д`.
- [ ] Прогресс-бары имеют разные цвета, подписи и адекватную шкалу.
- [ ] При перезапуске Host браузер видит Disconnected/Stale и корректно синхронизируется после возврата.

### Визуальные

- [ ] Основной фон `#1E293B`, верхняя полоса `#0F172A`, границы `#334155`.
- [ ] Classic Console Neue установлен как основной шрифт; кириллица отображается корректно.
- [ ] При ширинах 375, 768, 1280, 1920, 2560 и 3840 px сетка адаптируется, и на широких экранах число колонок может быть больше 3.
- [ ] Нет обрезания ключевых метрик или горизонтального скролла на типовых размерах.
- [ ] При длинном ID/названии карточки не ломают сетку.

### Безопасность и эксплуатация

- [ ] Неавторизованный запрос к API и SSE получает отказ; нельзя извлечь сведения о чужих сессиях через прямой URL.
- [ ] Отсутствует CORS `*`, не используются аккаунтные токены в браузере и логах.
- [ ] Сервер доступен только с localhost, если настройку сети явно не расширяли (в MVP расширение не поддерживается).
- [ ] Unload/reload освобождает слушатели и EventSource-клиентов.
- [ ] Никакие операции Dashboard не влияют на ход выполнения агентов.
- [ ] Плагин удаляется штатно без изменений исходников Harness.
